# 需求与规格

## 调查和澄清

先只读调查现有行为、相关代码、用户文档和已知约束。优先澄清范围/权限、数据安全、核心流程、失败恢复，以及性能、启动时间、内存、发布目标和兼容性。只询问会改变方案或造成明显风险的问题；可安全推断的内容写入“假设”，并说明依据。

## PD 中的建议结构

```markdown
# <功能名称>

## 文档信息
- Iteration: `Iter<number>-<Name>`
- Product Design: `PDnnnn-Name`
- Status: `draft | planned | in-progress | complete`

## 背景与目标
## 范围
### 包含
### 不包含
## 角色与用户场景
## 需求
### REQ-001 <单一、可观察的行为>
- 优先级：P1 | P2 | P3
- 验收场景：SC-001
  - Given ...
  - When ...
  - Then ...
## 非功能要求
## 边界与异常
## 假设与依赖
## 待确认项
```

每条需求只表达一个行为，并至少有一个可验证场景。场景描述结果，不指定 endpoint 类、路由实现、表名或框架。Native AOT、镜像体积和启动性能只有在构成用户或运维目标时才作为需求；具体实现约束写入设计。

PD 定稿时将它添加到 `Demand.md` 的迭代目录；如果包含重要设计决策，同时添加到 `Design.md` 索引。

## 质量清单

- 目标、成功指标、包含范围和排除范围明确；
- 角色、授权和数据归属清楚；
- 正常、空值、重复、冲突、无权限、超时和依赖失败路径按风险覆盖；
- 验收条件具体可测；
- 性能、容量、启动时间、内存、兼容、审计和可观测性按需量化；
- 没有实现细节污染需求，也没有未登记的隐含决定；
- 每个待确认项说明影响。

需求质量清单通过只代表意图足够清晰，不代表实现完成。
